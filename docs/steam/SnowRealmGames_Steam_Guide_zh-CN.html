发布手册 · 简体中文版 · 2026-11-18 核查

从网页游戏，走到可交付的 Steam 产品

适用项目：SnowRealm Games 游戏平台与《旋界》。覆盖浏览器 / PWA、电脑对战、线上房间、好友、排位、金币、道具、外观商城、订阅和自定义图片。未来的「52」与「电梯」应各自评估产品身份、权利和发行范围。

先明确交付边界

这份文件是可执行的上架路线与审核清单，不代表 Steam 已接收、审核或批准游戏。GitHub 源码、网站上线和 Steam 正式发行是三个不同的交付结果。

建议采用的首发路线

  • 继续把浏览器版作为主开发入口，共用游戏规则、五语文案和服务端；另做包含本地资源的 Windows 桌面发行包。
  • 先完成可独立运行的练习 / 电脑对战，再将实际通过验证的联机、排位和付费功能加入 Steam 商店承诺。
  • Steam 首发采用免费游玩 + 直接购买外观的设计；金币主要通过对局获得，道具限定在明确标识的派对模式。具体付费方案仍须完成平台审核。
  • 订阅、跨平台权益共享、公开图片分享和两款相近产品同时发行，先确认平台条件与运营能力，再开放收费。

必须 · 官方金额与时间单独列示

01 / 费用、身份与时间：先把硬条件算清楚

事项当前规则 / 口径来源
每个新应用的提交费USD 100 或等值当地货币；费用不退。达到至少 USD 1,000 调整后总收入后，可在后续付款中回收。不是缴费后立即退款。S01
首次几款产品的等待期支付该应用费用后，发行前至少等待 21 天。不要继续套用旧教程常见的 30 天版本。S02 / S03
Coming Soon商店「即将推出」页面须公开至少两周，才能正式发行。S02
税务资料验证可能最长达 30 天，也可能要求补充文件；与 21 天发行等待期属于不同事项。S02
商店页面审核通常 3-5 个工作日；官方建议至少提前 7 个工作日提交，留出修改空间。S04
游戏构建审核通常 3-5 个工作日；至少预留 7 个工作日。并非上传完成即通过。S04

核查日：2026-11-18。等待期以当前官网正文为依据；搜索快照、旧文章及旧版本文件可能仍显示不同数字。费用可能涉及当地税费，支付时确认最终金额。[S01][S02]

注册主体和收款资料

必须使用真实法律主体名称；银行账户户名须与入驻主体匹配。可以个人身份入驻，但不能把尚未注册的 SnowRealm Games 品牌名称当作法律姓名或公司名称。注册主体需要拥有发布产品的权利，并签署相应 NDA 和 Steam Distribution Agreement。[S02]

税务和收入不要混为一个百分比

税务问卷会根据身份和居住地生成预扣税结果。Steam 公布的美国来源收入预扣区间为 0%-30%；该数字不是整个平台的分成比例，也不能直接当作你最终的税率。不要假定台湾、其他地区或个人 / 公司身份适用相同规则。[S27]

建议 · 预算口径

用「玩家实际付款 - 退款 / 拒付 - 适用税费 - 合约分成 - 服务器 / 支付运营 / 客服 / 素材成本」建立现金流模型。分成和结算条件以自己签署的协议为准，不能仅凭“大家都说抽三成”做财务承诺。

建议流程 · 每个闸门都应有可查看证据

02 / 实际上架顺序与倒排计划

步骤具体动作完成证据
1. 主体准备确定个人或公司；整理法律姓名、地址、银行和税务资料。负责人确认，资料与收款主体一致。
2. Steamworks 入驻通过官方入口完成协议、应用费用、银行 / 税务 / 身份流程。后台状态通过；保存发票和应用编号。
3. 商店准备填商品信息、语言、系统需求、内容问卷与素材；说明在线账户要求。可预览的商店页面，内容符合实际版本。
4. 页面审核与公开提交商店审核；通过后发布 Coming Soon。公开页面网址及公开时间。
5. 封装与接入建立桌面包、Steam 身份、存档、支付适配和实际联机后端。全新电脑可装可玩，接口验收记录。
6. 测试与构建审核上传测试分支、安装验收、修复问题；提交接近最终版本。通过构建审核，锁定首发 Build ID。
7. 正式发布满足所有等待期；确认默认分支、价格 / 免费属性和服务器。授权负责人按 Release App，检查公开结果。

商店和构建是不同审核对象；发行由具备权限的账户通过后台发布控件执行。上传到 SteamPipe、选中某个构建、通过审核，都不等同于已经正式发行。[S04][S19]

如何计算最早发行日

以「支付费用 + 21 天」「Coming Soon 公开 + 两周」「身份与税务审核完成」「商店及构建通过」「真实服务可用」中最晚的时间为下限，再留出修复缓冲。几个等待条件可以重叠，但不能简单说交钱后第 21 天一定能上线。[S02][S04]

测试阶段的选择

建议先用 Steam Playtest 收集输入手感、匹配和联机反馈。Playtest 对开发者和玩家免费，不能卖测试资格、售卖 Playtest key，或把资格塞进付费订阅包。[S24]

Early Access 是销售当前可玩的未完成产品，当前版本本身必须值得其售价；它不是只卖未来承诺的众筹工具。若后端、核心对局或商业功能仍不稳定，应继续免费测试，而不是把“抢先体验”当作免检标签。[S30]

建议 · 共用游戏核心，增加桌面发行层

03 / 网页技术如何进入 Steam

浏览器 / PWA 继续保留。Steam 版需要向 Steam 提供能够安装和启动的产品构建，并在商店声明的操作系统上正常运行。仅给出一个网站网址或 GitHub 仓库，不能替代完整发行构建。[S04][S08]

层本项目建议首发验收
共享规则核心方块生成、旋转、Hold、计分和回放逻辑独立于网页界面。相同种子、规则版本和输入能复现结果。
浏览器版本保留链接直玩、PWA 安装和响应式界面。桌面与触控可操作；浏览器刷新不损坏持久数据。
桌面容器评估 Electron 或 Tauri 等方案；把游戏 HTML / JS / 图片 / 音频打入本地包。断网可进入已声明的单机内容；无空白网页或浏览器外跳依赖。
Steam 适配层封装 Steam 身份、语言、好友邀请、成就、支付等能力。不把 SDK 密钥或管理功能暴露给网页脚本。
SnowRealm 服务端统一账户、好友、匹配、对局验证、金币账本和权益。服务端验证身份；可以处理重试、退款、断线和回滚。

关于 Steamworks SDK 的准确说法

Steam 官方说明：发行游戏本身不强制集成所有 Steamworks API；但使用微交易、成就、Steam 身份等特定功能，需要按对应接口完成集成。SteamPipe 上传工具与游戏内 API 接入也不是同一件事。[S32][S08][S25]

桌面封装的工程注意事项

  • 锁定发布依赖和打包版本；保留构建来源、Git commit 与校验值。不要在发行包里附带 .env、私钥、数据库密码或开发账户。
  • 本地游戏资源优先。远程内容更新应有版本兼容和回滚设计；不要让网页一次部署就悄悄破坏已审核桌面版本。
  • 桌面壳只暴露必要能力。自定义图片不能执行脚本，不能任意访问系统路径；外部链接限制用途和目标。
  • Windows 首发先做实机验证；macOS / Linux 后续各自提供可测试构建，验证之前不要在商店勾选支持。
待核实

桌面桥接库的维护状况、许可证、架构支持及 Steam Overlay 行为，需要按最终选型做小型验证；“能把网页装进窗口”不等于 Steam 支付、手柄和 Overlay 已经兼容。

操作教程 · 以下占位符必须换成你的后台编号

04 / SteamPipe 上传：从文件到可安装构建

  • 在 Steamworks 取得 App ID，配置对应平台的 depot、启动文件和启动选项。
  • 下载官方 SDK，使用 tools/ContentBuilder；将成品桌面文件放入 content 下的项目目录。
  • 建立仅具备必要权限的构建账户。官方建议构建账户拥有 Edit App Metadata 与 Publish App Changes To Steam 等所需权限，不复用个人最高权限账户。[S08]
  • 编写 app 和 depot VDF；先上传私人测试分支，使用测试账户从 Steam 客户端实际下载安装。
  • 确认文件、语言、运行库、存档、Overlay 和退出行为后，再选定要提交审核的构建。

最小 VDF 结构示例

"AppBuild"
{
  "AppID" "YOUR_APP_ID"
  "Desc" "spinrealm-review-candidate"
  "ContentRoot" "../content/spinrealm"
  "BuildOutput" "../output"
  "Depots"
  {
    "YOUR_DEPOT_ID" "depot_windows.vdf"
  }
}

"DepotBuildConfig"
{
  "DepotID" "YOUR_DEPOT_ID"
  "FileMapping"
  {
    "LocalPath" "*"
    "DepotPath" "."
    "recursive" "1"
  }
}

这是两个文件的结构展示，分别保存为 app_build.vdf 和 depot_windows.vdf，并核对相对目录。此示例故意不指定 SetLive，避免上传时意外切换公开分支。正式参数和 SDK 目录以官方上传文档为准。[S08]

发布账户与密钥

已发行产品把新构建设为默认分支时，Steam 有额外授权环节。官方文档说明该账户需要绑定电话号码或 Steam Mobile App；部分账户安全信息修改还会触发 3 天等待。不要把更新计划压在同一天修改账户安全资料。[S08]

密码不写入仓库、VDF 或展示用命令；使用受控构建环境。保存成功的 Build ID、commit、版本说明和回滚目标，形成可追溯发布记录。

建议 · 一套主账户，多种经过验证的登录入口

05 / SnowRealm 会员、Steam 身份与好友

推荐的账户流程

  • 获取 Steam 官方身份票据，交由 SnowRealm 后端验证，通过后才创建或登录内部用户。
  • 已有账户的玩家主动绑定，并验证两边账户的所有权。不可按昵称、头像或玩家填写的 SteamID 自动合并。
  • 网页 Steam 登录可采用官方 OpenID，与游戏内票据流程不同；任何页面都不应索取 Steam 密码。[S09]
  • 展示关联状态、退出、设备会话和客服入口。解绑、迁移和重复绑定须有明确规则，避免权益转移漏洞。

Steam Publisher Web API key 仅保存在安全服务器。官方要求这类受保护请求来自服务器，密钥不能随客户端分发，涉及密钥的请求使用 HTTPS。[S17]

数据 / 功能建议归属注意点
SnowRealm 用户编号平台后端作为跨游戏主键，不使用可修改的昵称。
SteamID 绑定平台后端保存已验证的外部身份关联和绑定时间。
好友关系平台后端好友申请、接受、拒绝、拉黑、撤回和权限控制。
Steam 好友邀请Steam 适配 + 房间服务收到邀请后仍验证房间、版本和成员权限。
在线状态平台后端提供隐身或可见范围；不公开邮箱或登录标识。
订阅和购买权益服务端权益账本按平台、订单和有效期记录，不相信本地开关。

Steam Lobbies 可以帮助邀请和发现同一大厅中的玩家，但不会自动替你完成跨浏览器账户系统、排位规则和防作弊。跨平台房间仍需要自己的协议和可验证的对局服务。[S31]

离线与登录边界

建议练习、电脑对战和本地设置允许离线；匹配、好友、排位和付费权益同步显示网络需求。离线分数不能未经验证直接兑换线上金币或提交排位。商店须如实披露第三方账户与联网要求，并说明断网可玩哪些内容。[S04]

建议 · 将公平性写进规则和账本

06 / 得分、金币、排位：有后端才有可信结果

积分、金币和段位是三套不同数据。积分描述本局表现；金币是经济资产；段位描述匹配和竞技结果。把三者全部保存在浏览器 localStorage，玩家就能直接修改结果，因此不适合作为正式线上经济和排行榜的依据。

系统建议设计不可省略的校验
本局得分固定规则版本；记录消行、旋转、连击与其他奖励来源。服务器复算或验证输入 / 回放；同一局只结算一次。
金币对局结算、任务和活动奖励逐笔入账。唯一事件编号、幂等性、余额约束、变动原因。
道具购买公开固定价格；不足余额时阻止交易。扣款和发货同一事务；重试不会重复扣币。
道具使用仅派对房间开放；开局前展示规则。消耗库存、冷却、目标和使用时间由服务端确认。
排位规则一致、同等性能、无付费增益；赛季独立。匹配版本、断线处理、异常结果、重赛和申诉。
皮肤权益外观不改变碰撞、下落速度或得分。所有权检查；退款 / 到期后恢复合法可用外观。

Steam 排行榜如何接

Steam Leaderboards 可以设置 Trusted 写入：客户端不能直接提交分数，只能由相应 Web API 写入。建议正式榜单用可信后端提交，并保留可审计的结算与回放记录。Steam 排行榜只是显示和排序能力，不会自动证明比赛真实有效。[S14]

需要的对局服务最小集合

  • 匹配服务分清练习、休闲、道具派对、排位和团队；排位队列不混入未告知的机器人。
  • 房间记录规则版本、玩家和随机种子；服务端验证关键输入、攻击和结束结果。
  • 断线有明确的重连窗口与判负规则。超时、双方掉线和服务异常必须可以区分。
  • 控制异常操作频率、脚本刷币、重复结算与账户串通；封禁和更正结果保留审计及申诉渠道。
产品取舍

先让排位可信，再让排位热闹。付费用户如果能买到竞技优势，短期多卖道具，长期会把最愿意持续玩的核心玩家赶走。此处是商业与玩法建议，不是 Steam 对所有游戏强制规定的模式。

建议方案 · 不把价格或订阅开通状态当作已确认事实

07 / 商业模式：外观订阅可以做，边界先定好

项目建议卖点边界与风险
免费基础体验练习、电脑对战、核心匹配；基础皮肤与输入设置完整。不要以更差手感或不可读棋盘强迫购买。
直接购买外观主题、方块材质、棋盘背景、音效风格、个人展示。明确预览与价格；不影响竞技判定。
订阅会员自定义图片、扩展外观库、更多预设、跨设备保存。必须有持续服务价值；到期保留什么写清楚。
金币与道具金币兑换派对道具或部分外观。首发建议金币靠游戏获得；不开放提现和玩家转卖。
支持者礼包固定内容和清楚的永久权益。适合作为更容易理解的一次性选择；仍须平台审核。
活动与赛季免费赛季目标、赛事、可选装饰。付费通行证不要承诺尚未确定且无法兑现的内容。

Steam 版支付规则

游戏内交易必须使用 Steam Wallet 对应的微交易流程。不能在 Steam 游戏内把玩家带到不提供 Steam Wallet 的其他商店支付。网页上已有的 Stripe、信用卡或其他收款按钮，应由发行平台适配层处理，不能原样嵌入 Steam 构建。[S04][S06]

广告模式需要调整

Steam 官方不支持游戏以付费广告为商业模式，也不支持看广告换金币、体力、道具或其他价值。若浏览器版以后加入奖励广告，Steam 版本必须移除对应机制；不要把“自愿看广告”误当作例外。[S16]

如何定价与验证

先用免费测试测量用户留存、每位活跃用户的服务成本、外观预览转化和长期留存，再决定各地区价格。订阅应有月度内容 / 存储 / 服务的真实成本与价值；单纯开放本地选图功能是否足以支撑月费，需要用户实验验证。不要把尚未得到验证的价目表称为最终方案。

建议付费前清楚展示包含内容、自动续费与否、期限、取消入口、退款方式、图像保存和到期行为。首发减少付费品类，可以降低订单异常、客服和翻译维护成本。

必须 + 建议 · 支付成功以服务端结果为准

08 / 订单、订阅、退款与跨平台权益

微交易的实现顺序

服务端创建唯一订单，调用 InitTxn；玩家在 Steam 内授权后，服务端通过 FinalizeTxn 完成交易，成功后再发放物品。用 GetReport 持续对账，并处理退款、部分退款、拒付和疑似欺诈状态。官方要求至少每天核对交易状态；高频业务可更频繁。[S25]

工程建议：授权回调可以重放，发货接口必须幂等；购买失败不扣金币、不发货。每项权益都能追溯到平台、订单、商品、实际有效期与回收原因，退款不能只删除一条订单记录。

订阅不能直接照搬网站会员

官方 Recurring Subscriptions 文档仍将其标为未完全支持的功能；自动续费需要用户同意的协议与相应计费流程，开发者负责到期和周期处理，不能任意提高约定的周期金额。实施前向 Steamworks 确认本项目的适用方案、测试方式与取消路径。[S07]

建议先验证一次性外观购买。需要长期会员时，比较自动续费与非自动续费的固定期限权益；后者也须明确商品类型、发放与退款规则，不能用换个名字绕过支付要求。

类型官方退款口径摘要产品实现
普通游戏购买通常购买 14 天内且游玩少于 2 小时可申请。不要以强制等待、刷时长方式阻碍退款。
DLC通常 14 天内，购买 DLC 后基础游戏游玩少于 2 小时，且未消耗 / 修改 / 转移；存在标示的例外。服务端记录可撤回权益，按真实退款状态处理。
第三方游戏内购48 小时退款不是对所有第三方内购的统一承诺；是否提供该机制取决于开发者选择及显示条件。上线前确认选项与实际购买页提示。
自动续费订阅当前周期未使用时，通常可在首次购买或自动续费后 48 小时内申请；可取消后续续费。取消与立即退款分开；明确剩余周期访问权。

本表仅摘要，完整条件、适用例外和消费者法定权利以 Steam 退款页为准；核查日 2026-11-18。[S12]

待核实 · 跨平台共享

SnowRealm 可以设计统一权益账本，但 Steam 购买、网页购买、跨游戏订阅、虚拟币互通和付费道具共享的具体许可不能从“有一个账号”推导出来。提交商品及流转图给 Steamworks 确认，未确认前不要承诺全平台通用。

09 / 自定义图片：私人背景与公开分享

“会员可以上传自己的图片”会产生文件处理、隐私、版权和内容管理需求。建议首版仅允许玩家在自己的界面中使用，默认不展示给对手、不进入公开图库；公开分享、好友可见和创作者商店另行设计。

环节首版建议公开分享前增加
上传限已知图片格式；检查真实文件类型、尺寸和解码结果。隔离处理、内容检测、人工复核和异常隔离。
图片处理重编码成安全格式，剥离不必要元数据；生成适配尺寸。多级预览、违规图屏蔽、撤回后的缓存清理。
存储按用户隔离；私有权限或短期访问凭证；允许删除。可见范围、举报、审核状态与管理员审计。
对局显示本人看到自己的背景；默认竞技背景可一键恢复。对手可关闭他人的图片，屏蔽状态全端生效。
订阅到期事先说明保存多久、是否还能使用、如何导出 / 删除。限制上传与删除账号的边界不能冲突。
用户责任确认有使用权；禁止上传侵犯他人权益或违法内容。明确发布许可、举报处理、申诉和下架流程。

私有也要有安全边界

本地选图不必自动上传服务器。若需要跨设备同步，应告诉玩家存储位置类别、用途、保留期限、删除方式和服务提供者范围。不要把图片默认为可用于训练或推广；如需要其他用途，另行说明并取得适当授权。隐私和未成年人措施须结合目标市场实际法律审查，本文件不代替法律意见。

如果接 Steam Workshop

Workshop 提供现成内容分发与社区能力，但接入仍需要上传路径、下载加载和内容验证。官方区分自由发布与精选内容模式；付费精选物品还需要持久的所有权记录及购买界面。因此“支持自定义背景”并不等同于已经支持 Workshop。[S22]

Steam 的社区管理工具可对不合适、违规或被盗用的内容进行处理；这不取代你对自建图片服务器、游戏内昵称、聊天、头像和好友骚扰的处理流程。首发至少落实举报、拉黑、禁用公开图像和客服响应责任。[S23]

建议 · 可读性不能变成付费负担

每个主题都必须保持方块轮廓、落点、垃圾行和危险提示可辨。提供背景暗化、不透明度、默认背景与减少动态效果，让玩家能把图片调成“好看而不挡手”。

必须 · 权利记录比“网上免费下载”更重要

10 / 素材、商标、生成式 AI 与内容分级

建立素材权利清单

Steam 不接受缺少所有权或足够授权的内容。[S02] 对音乐、音效、字体、图标、背景、方块样式、宣传图和代码依赖，保存名称、作者、原始网址、许可证版本、取得日期、允许的商用 / 修改 / 再分发范围、署名文本和证据文件。

免费不等于开源，开源也不等于没有义务。素材许可必须覆盖游戏内使用、Steam 下载包、宣传视频和可能的付费外观；音源、采样和字体也要分别核对。若“许可只允许在作品中使用”而不允许单独转售，就不能把原始素材包装成可下载素材包卖给用户。此处为权利核查方法，不是对未见许可证的结论。

不要把怀旧做成官方身份误认

Tetris 官方条款明确保护其名称、商标、标志和网站内容。不要从旧 Tetris Battle 或现有 Tetris 产品直接复制美术、音乐、文案、界面素材或代码，也不要把《旋界》宣传为官方续作、授权版本或官方复活。[S28]

建议使用原创名称、视觉语言、音景和规则表达。某一具体玩法、画面组合或商标使用是否构成侵权，需要由具资格的专业人士按目标市场评估；“换了名字”并不是对所有知识产权问题的通行证。

生成式 AI 内容问卷如何填

必须完成 Steam 内容问卷。AI 部分聚焦玩家实际消费的生成内容，包括图像、音频、叙事和本地化等；单纯提升开发效率的工具使用不是同一口径。若交付的五语翻译或美术由生成式 AI 产生，应按当前问卷如实说明。预生成与游玩时实时生成的内容须分别处理；实时生成还需说明防止非法内容的措施。[S05]

分级与地区

真实完成一般内容、成人内容和 AI 三部分，未公开但随包上传的成人内容也不能隐瞒。自定义图像、聊天和社区分享会改变内容风险，应在功能变化后重新核对问卷。[S05]

德国商店要求有效年龄评级；没有有效评级的游戏自 2024-11-15 起不向当地顾客显示。填写问卷是 Valve 自评流程的重要输入，但不保证所有内容都能在德国销售。未经对应机构实际评定，不要自行填写 USK 评级。[S26]

12 / 操作手感、可及性与 Steam Deck

把核心操作做成可配置的能力

建议提供左右移动、软降、硬降、顺 / 逆时针旋转、Hold、暂停 / 返回以及派对道具的独立按键映射。界面要显示冲突、允许恢复默认、支持左右手预设，并分别保存键盘与手柄配置。不要让聊天输入和游戏快捷键同时触发。

DAS、ARR、锁定延迟等手感设置要有清楚解释和安全默认值。皮肤、背景动画、音乐和粒子效果不应拖慢输入处理；音乐与音效分开音量，提供一键静音和减少闪烁 / 动态效果。

Steam Deck 的明确检查项

官方兼容性检查涉及完整手柄导航、正确按键提示、文本输入、启动器可操作与 Proton 兼容。Deck 推荐支持 1280×800 或 1280×720；在 1280×800 时最小文字字形高度不能低于 9 px，官方建议尽量达到 12 px。默认性能门槛与其他细项以完整检查表为准。[S13]

对《旋界》的工程目标可设为稳定 60 FPS 和低输入延迟；这是本项目建议，不是把官方兼容性最低门槛改写成 60 FPS。必须在真实设备或等效环境实测，不能只看开发电脑的帧数。

场景验收重点
仅键盘菜单、设置、登录后的游戏流程、对局和退出都可完成。
仅手柄焦点可见；不需要鼠标点网页；输入昵称时有可用软键盘。
换肤 / 自定义背景方块边界与落点仍清晰；色彩不是唯一提示。
繁 / 简 / 日 / 韩字体无缺字；长句不被截断；字号可调时布局稳定。
暂停 / 失焦 / 休眠单机可恢复；线上明确断线状态，不重复结算。
音频关闭危险和成功提示仍有视觉反馈；设置重新启动后保留。

Steam 提供可及性功能声明入口。只勾选真正完成的音量、文字大小、颜色替代、对比度或输入能力；例如允许改变背景颜色，不自动意味着整个游戏已满足“无视觉游玩”。[S29]

必须准确描述

Deck Verified 等兼容标识由 Valve 的实际评审产生；未评审前只能描述自己的测试结果，不能自行宣称官方认证。[S13]

13 / 成就、云存档与发布前测试

成就和存档分工

Steam Stats and Achievements 支持持久统计和本地化成就信息。建议首批成就围绕完成教学、旋转技巧、练习里程碑和合作行为，而不是用金币付费解锁的荣誉。与线上竞技结果有关的成就应来自可信结算。[S33]

Steam Cloud 可以同步存档文件，Auto-Cloud 也能按路径配置。建议同步单机纪录、键位、主题预设，按 Steam 用户隔离存档；机器专属显示设置避免盲目跨设备覆盖。金币、段位和订阅的权威状态仍放服务端，不能把 Cloud 文件当支付数据库。[S15]

14 / 发售当天与长期运营

上线前最后检查

  • 商店与构建已通过；等待期满足；Steam 后台选择的是预定 Build ID；所有支持平台与语言验证完成。[S04][S19]

  • 客服邮箱 / 工单、状态页、举报处理与值班负责人可用；公告和常见问题准备五语最少必要版本。

建议 · 比较产品结果，避免把人群差异误当代码优劣

15 / 两个实现都上线：怎么比较才有意义

你准备让不同实现分别上线，这可以验证玩法与手感方向；但两个相近产品会分散玩家、好友关系和匹配人数。产品需要有玩家能理解的区别，例如竞速竞技与道具派对，而不是只因为开发工具不同就要求玩家理解两款商品。

发行结构选择

选择适用情形代价
同一产品的测试版本 / 模式规则和品牌基本一致，只比较操作与界面。不适合把多个不兼容客户端随意混入同一排位。
两个独立产品玩法、定位、内容和长期维护计划有明确差异。各自费用、审核、商店、客服与玩家池；需解释关系。
先网页比较，再决定 Steam需要快速测首局转化与留存。网页数据不自动代表 Steam 用户偏好。

本次核查没有发现一条公开规则足以保证两款高度相似游戏会通过审核。应把差异说明、截图、内容与维护承诺提交 Steamworks 询问，而不是承诺“只要两个 App ID 就一定没问题”。每个独立新应用的费用按官方规则分别计算。[S01]

公平实验的建议

  • 记录来源渠道、地区、设备、时间段和熟练度；在相近招募条件下比较。
  • 同时看首局完成、输入满意度、七日留存、有效对局和好友邀请，不只看累计注册数。
  • 记录两版本的内容、活动和价格差异；不能把一个版本有广告曝光、另一个没有带来的流量差异当成技术胜负。
  • 跨版本账号和资产共享先定规则；排位算法、反作弊和付费价值不同，不应未经验证直接混排或互换。

评论与评价边界

Steam 禁止操纵评价和用游戏、DLC、钱或其他奖励换评价，官方也要求不要在游戏内请求玩家写评测。不要用“评价送金币”、组织刷好评或多个账户投票比较两个版本；免费给媒体 / 内容创作者评测样本的例外也不意味着可以买正面结论。[S18]

判断标准

更值得留下的不是“哪边代码写得更快”，而是哪个版本让玩家愿意持续回来、愿意邀请朋友，并且运营成本可承受。两个版本的数据应帮助做选择，而不是永久维持两套几乎相同的维护负担。

提交给 Steamworks 的问题应具体到方案

  • 《旋界》拟以免费核心 + 付费外观发行；会员包含自定义图片、云端保存和外观库。哪种订阅 / 固定期限商品配置适合？自动续费是否可启用，如何测试取消和退款？
  • Steam 和网页版共用 SnowRealm 账户。哪些已购买外观 / 虚拟币 / 订阅权益可以跨平台使用？Steam 客户端应如何呈现跨平台状态而不违规引导外部支付？
  • 未来会员若覆盖「旋界、52、电梯」，该跨游戏权益范围是否符合相应产品与计费设置？
  • 两款类似方块游戏将各自发布：附上真实差异、截图、玩法和维护计划，请确认应使用独立 App、模式、Demo 还是其他结构。
  • 图片最初为私人自用，将来可能加入公开分享与创作者内容；内容问卷、Workshop 和审核应在何时更新？

不要把问题只写成“能不能上架”。附可运行构建、商品流转图、权益到期示例、退款处理和具体商店文案，更容易得到能执行的答复。保留支持工单编号和答复日期。
